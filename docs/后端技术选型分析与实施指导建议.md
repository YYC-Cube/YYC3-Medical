## 1. 现状与约束分析

### 1.1 前端已有契约（不可破坏）

前端已定义完整的 API 契约层,**后端必须严格遵守**：

| 层 | 文件 | 约束 |
|----|------|------|
| API Client | `lib/api/client.ts` | `fetch` 封装,Base URL = `NEXT_PUBLIC_API_BASE_URL \|\| "/api"`,支持 `params`/`requiresAuth`/`cache`/`revalidate` |
| Endpoints | `lib/api/endpoints.ts`(109 行) | 定义了 AUTH/USERS/PATIENTS/MEDICAL_RECORDS/AI_DIAGNOSIS/CASE_LIBRARY 等 8 大模块的端点路径 |
| Auth | `lib/auth/jwt.ts` | 用 `jose` 做客户端 JWT 验签,期望后端签发 HS256 JWT |
| Env | `lib/env.ts` | `DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL`/`NEXT_PUBLIC_APP_URL`/`NEXT_PUBLIC_APP_VERSION` |
| Services | 31 个 `services/*.ts` | 返回 mock 数据,但函数签名即为后端 API 契约 |

**关键约束**：

- 前端路径以 `/api` 为前缀(可通过 `NEXT_PUBLIC_API_BASE_URL` 覆盖)
- 前端用 `trailingSlash: true`,期望后端路由也容忍/匹配尾部斜杠
- Prisma schema 已定义 MySQL（7 个 model + 5 个 enum），但**数据库选型可改**（详见 §5）

### 1.2 业务领域模型

从前端 112 个页面 + 31 个 service + 439 个组件,可归纳出 **9 大业务域**：

| 域 | 核心实体 | 读写比 | 特殊需求 |
|----|---------|--------|---------|
| 患者管理 | Patient / MedicalRecord / FollowUp | 读多写少 | PHI 加密、按权限过滤 |
| AI 诊断 | Diagnosis / ModelVariant / ABTest | 读少写多(推理) | 长耗时请求、流式响应 |
| 临床决策 | Guideline / DrugInteraction / Pathway | 读极多 | 知识库预加载、RAG |
| 病例库 | Case / CaseComment / CaseImage | 读写均衡 | 全文搜索、相似度 |
| 科研管理 | Experiment / Sample / Trial | 读写均衡 | 多中心协作、权限分层 |
| 知识图谱 | GraphNode / GraphRelation | 读极多 | 图查询、10 万+节点 |
| 药物管理 | Medication / Prescription / Inventory | 读写均衡 | 药物互作实时查询 |
| 系统管理 | User / Role / AuditLog / Config | 读多写少 | 审计日志不可篡改 |
| 远程会诊 | Consultation / Message / File | 读写均衡 | WebSocket 实时通信 |

### 1.3 非功能性需求（NFR）

| 维度 | 要求 | 依据 |
|------|------|------|
| **可用性** | 99.9%（年停机 ≤8.7h） | 医疗系统不可随意宕机 |
| **响应延迟** | API P95 ≤500ms（非 AI）、≤5s（AI 推理） | 临床场景要求 |
| **数据安全** | PHI at-rest + in-transit 加密 | HIPAA / PIPL / 等保三级 |
| **并发** | 500 并发用户 / 2000 QPS | 中型医院规模 |
| **数据量** | 100 万患者 × 50 条记录 = 5000 万行 | 3 年预估 |
| **审计** | 所有敏感操作落库,保留 ≥5 年 | 等保 / NMPA |
| **合规** | 等保 2.0 三级、IEC 62304、ISO 14971 | 医疗器械软件 |

## 2. 核心架构决策：3 种方案对比

### 方案 A：Next.js 全栈（取消静态导出）✘ 不推荐

**描述**：移除 `output: 'export'`，启用 Next.js App Router 的 Server Actions + API Routes + RSC，前后端同体部署。

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★★★ 最快（单一代码库、TS 类型端到端共享） |
| 运维成本 | ★★★★☆ 较低（单一部署单元） |
| 扩展性 | ★★☆☆☆ 差（Next.js 不适合重后端逻辑、AI 推理长任务） |
| 合规隔离 | ★★☆☆☆ 差（PHI 与前端代码混部,审计边界模糊） |
| 已有前端兼容 | ★☆☆☆☆ 极差（需重构 112 个页面的数据获取模式,大部分 `"use client"` 组件需改为 RSC） |

**否决理由**：
- 医疗系统的后端需要复杂的事务、队列、定时任务、WebSocket —— 这些不是 Next.js 的强项
- PHI 数据不能与静态前端同进程,合规上需要物理隔离
- 现有前端是纯静态导出,改为全栈模式意味着推翻已验证的部署架构

### 方案 B：Next.js + 独立 NestJS 后端 ✓ 推荐

**描述**：保留前端纯静态导出不变，新建独立的 NestJS 后端服务，前端通过 HTTP/REST 调用。

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★★☆ 高（NestJS 装饰器 + DI + 模块化，TS 端到端） |
| 运维成本 | ★★★☆☆ 中（两个部署单元,但可独立扩缩容） |
| 扩展性 | ★★★★★ 优（微服务就绪、队列/缓存/WS 原生支持） |
| 合规隔离 | ★★★★★ 优（PHI 完全在后端，前端零接触） |
| 已有前端兼容 | ★★★★★ 完美（前端 `lib/api/client.ts` 已是 REST 客户端，零改动） |
| 团队招聘 | ★★★★☆ TS 全栈,前后端技能可复用 |

### 方案 C：Next.js + 独立 Python (FastAPI) 后端 ✘ 次推荐

**描述**：前端不变，后端用 FastAPI。

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★☆☆ 中（Python + TS 双语言栈,类型不能端到端共享） |
| 运维成本 | ★★★☆☆ 中（双语言工具链） |
| AI/ML 生态 | ★★★★★ 最强（Python 是 ML 第一语言，PyTorch/transformers/onnxruntime 原生） |
| 合规隔离 | ★★★★★ 优 |
| 已有前端兼容 | ★★★★☆ 良（需用 OpenAPI 生成 TS 类型,多一层代码生成） |
| 团队招聘 | ★★★☆☆ 需要 Python + TS 双语言人才 |

### 对比总结矩阵

| 维度 | 方案 A (Next 全栈) | 方案 B (NestJS) ✅ | 方案 C (FastAPI) |
|------|-------------------|-------------------|------------------|
| 前端改动量 | 🔴 巨大 | 🟢 零 | 🟢 零 |
| TS 端到端类型 | ✅ | ✅ | 🔴 需 codegen |
| AI 推理集成 | 🔴 弱 | 🟡 中(调 Python 微服务) | ✅ 原生 |
| 微服务演进 | 🔴 | ✅ | ✅ |
| 团队技能复用 | ✅ | ✅ | 🔴 双语言 |
| 合规隔离 | 🔴 | ✅ | ✅ |
| 生态成熟度 | ✅ | ✅ | ✅ |
| **综合** | **✘ 否决** | **✅ 推荐** | **🟡 备选(AI 微服务)** |

**选型理由**：

1. **前端零改动**：NestJS 的路由 `/api/patients` 完全匹配前端已定义的 `API_ENDPOINTS.PATIENTS.LIST = "/patients"`，只需设置 `NEXT_PUBLIC_API_BASE_URL=https://api.yyc3-med.com`。

2. **TS 端后端**：NestJS 用 TypeScript，前后端可共享类型定义（通过 monorepo 或 npm 包），消除序列化层类型漂移。

3. **AI 能力不妥协**：Python 微服务专注 AI 推理（LLM 调用、影像分析、RAG），NestJS 通过 gRPC/HTTP 调用。这保留了 Python ML 生态的全部优势，同时后端业务逻辑用 TS 统一。

4. **合规友好**：PHI 数据完全在 NestJS + PostgreSQL 内，前端静态资源零 PHI。审计日志在 NestJS 层统一拦截。

5. **渐进式启动**：可以先用 NestJS 实现核心 CRUD + 鉴权，AI 微服务后期再加。

## 4. 技术栈逐层选型

### 4.1 后端框架

| 候选 | 选型 | 理由 |
|------|------|------|
| **NestJS 11** ✅ | 企业级 Node.js 框架 | DI/IoC、模块化、装饰器、OpenAPI 自动生成、微服务原生支持、社区活跃 |
| Express | 太底层 | 需要手写中间件链,不适合中大型项目 |
| Fastify | 性能优但生态小 | NestJS 底层可切 Fastify adapter,两全其美 |
| Koa | 维护减弱 | — |

### 4.2 ORM

| 候选 | 选型 | 理由 |
|------|------|------|
| **Prisma 6** ✅ | 项目已有 schema.prisma | 类型安全、迁移工具完善、Introspection 能力、文档优秀 |
| TypeORM | 装饰器风格但 bug 多 | 维护质量下降 |
| Drizzle | 新星但生态未成熟 | 生产环境验证不足 |
| Sequelize | 老旧 | — |

> ⚠️ **Prisma schema 调整**：现有 schema 用 MySQL。建议迁移到 **PostgreSQL**（详见 §5）。

### 4.3 数据库

| 候选 | 选型 | 理由 |
|------|------|------|
| **PostgreSQL 16** ✅ | 关系型主库 | 详见 §5 |
| MySQL 8 | 现有 prisma schema 指定 | 不支持 pgvector、全文中文搜索弱 |
| MongoDB | 文档型 | 医疗数据强关系型,不合适 |

### 4.4 缓存

| 候选 | 选型 | 理由 |
|------|------|------|
| **Redis 7** ✅ | 内存数据库 | 会话/缓存/限流/队列/BullMQ 后端 |
| Memcached | 仅缓存 | 功能单一 |

### 4.5 消息队列

| 候选 | 选型 | 理由 |
|------|------|------|
| **BullMQ** ✅ | Node.js 原生队列 | 基于 Redis、NestJS 有 `@nestjs/bullmq`、支持定时任务/重试/优先级 |
| RabbitMQ | 功能强但重 | 医院内部部署运维成本高 |
| Kafka | 过度设计 | 适合日志流,不适合业务队列 |

### 4.6 实时通信

| 候选 | 选型 | 理由 |
|------|------|------|
| **Socket.IO** ✅ | WebSocket 库 | NestJS `@nestjs/platform-socket.io` 原生支持、自动重连、房间/命名空间 |
| 原生 WS | 轻量但功能少 | — |

### 4.7 AI 推理（Python 微服务）

| 组件 | 选型 | 理由 |
|------|------|------|
| 框架 | **FastAPI 0.115+** | 异步、自动 OpenAPI、Pydantic 验证 |

## 5. 数据库设计指导

### 5.1 为什么从 MySQL 改为 PostgreSQL

| 特性 | MySQL 8 | PostgreSQL 16 | 影响 |
|------|---------|---------------|------|
| 向量检索 | 无原生支持 | **pgvector** 扩展 ✅ | RAG/相似病例检索必备 |
| 全文搜索(中文) | 弱(ngram 分词) | **pg_jieba** / ZhParser ✅ | 病例库搜索 |
| JSON 操作 | 基础 | **JSONB + GIN 索引** ✅ | 灵活的医学元数据 |
| 数组类型 | 无 | **原生数组** ✅ | 标签/症状列表 |
| 事务隔离 | RR(有 gap lock 问题) | **SSI(Serializable Snapshot Isolation)** ✅ | 医疗数据一致性 |
| GIS | 基础 | **PostGIS** ✅ | 多中心地理分析 |
| Prisma 支持 | ✅ | ✅ | 无差异 |

**结论**：pgvector 是决定性因素 —— 路线图阶段 3 需要 RAG 检索,MySQL 无法原生支持。

### 5.2 数据库迁移指导

```bash
# 1. 修改 prisma/schema.prisma
#    datasource db { provider = "postgresql" }
# 2. 生成迁移
npx prisma migrate dev --name init-postgresql
# 3. 推送到新库
npx prisma db push
```

### 5.3 Schema 扩展建议

现有 7 个 model 需扩展至 ~25 个以覆盖 9 大业务域：

```
// 核心域(已有,需调整)
User / Patient / MedicalRecord / AuditLog

// 需新增
├── auth/        → RefreshToken / PasswordReset
├── patient/     → FollowUp / PatientGroup / Allergy / MedicationHistory
├── diagnosis/   → DiagnosisSession / DifferentialDiagnosis / RiskAssessment
├── ai/          → ModelRegistry / ModelVariant / ABTest / InferenceLog
├── clinical/    → Guideline / ClinicalPathway / DrugInteraction
├── research/    → Experiment / Sample / TrialSite / InformedConsent
├── knowledge/   → GraphNode / GraphRelation / KnowledgeArticle
├── case/        → Case / CaseComment / CaseImage / CaseTag
├── medication/  → Medication / Prescription / InventoryItem
├── consult/     → Consultation / ConsultMessage / ConsultFile
└── system/      → SystemConfig / Notification / FileAsset
```

### 5.4 关键设计原则

1. **PHI 字段加密**：患者姓名/身份证/电话 用应用层加密(AES-256-GCM)存储，密钥用 KMS 管理
2. **软删除**：所有业务表加 `deleted_at TIMESTAMPTZ`，医疗数据不可物理删除
3. **审计触发器**：对 PHI 表的 INSERT/UPDATE/DELETE 自动写入 `AuditLog`
4. **多租户预留**：所有表加 `organization_id`，为未来 SaaS 化铺路
5. **时区统一**：所有时间字段用 `TIMESTAMPTZ`（不是 `TIMESTAMP`），存储 UTC

## 6. API 设计规范

### 6.1 RESTful 约定

| 方法 | 用途 | 示例 |
|------|------|------|
| GET | 列表/详情 | `GET /patients?page=1&limit=20&search=张` |
| POST | 创建 | `POST /patients` |
| PATCH | 部分更新 | `PATCH /patients/:id` |
| DELETE | 软删除 | `DELETE /patients/:id` |

> **不用 PUT**（PATCH 更语义化且省带宽）。**不用 POST 做 DELETE**（遵循 REST）。

### 6.2 响应格式

```typescript
// 成功
{
  "data": T,              // 单个对象或数组
  "meta": {               // 仅列表请求
    "page": 1,
    "limit": 20,
    "total": 156,
    "totalPages": 8
  }
}

// 错误
{
  "error": {
    "code": "VALIDATION_ERROR",      // 机器可读
    "message": "邮箱格式不正确",       // 人类可读
    "details": [                      // 字段级错误(可选)
      { "field": "email", "message": "..." }
    ],
    "requestId": "req_abc123"         // 追踪 ID
  }
}
```

### 6.3 认证

```
Authorization: Bearer <access_token>
```

- Access Token: HS256 JWT, **15 分钟过期**
- Refresh Token: 随机 opaque token, **7 天过期**, 存 Redis + HttpOnly Cookie
- Token 刷新: `POST /auth/refresh`（refresh_token in cookie）

### 6.4 分页/排序/过滤

```
GET /patients?page=1&limit=20&sort=-created_at&filter[status]=active
```

- `sort=-created_at`：负号 = 降序
- `filter[field]=value`：等值过滤
- `filter[age][gte]=18`：范围过滤
- `q=关键词`：全文搜索

### 6.5 幂等性

```
POST /diagnoses
Idempotency-Key: client-generated-uuid
```

防止 AI 推理请求因网络重试导致重复计费。

### 6.6 速率限制

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 99
X-RateLimit-Reset: 1720000000
```

- 普通接口：100 req/min/user
- AI 推理接口：10 req/min/user
- 登录接口：5 req/min/ip

## 7. 鉴权与安全架构

### 7.1 认证流程

```
┌──────┐     POST /auth/login      ┌──────────┐
│ 前端 │ ─────────────────────────→ │ NestJS   │
│      │ ←───────────────────────── │          │
│      │  { access_token (15m) }    │  验证密码 │
│      │  Set-Cookie: refresh_token │  签发JWT │
└──────┘                            └──────────┘

┌──────┐  Request + Bearer token   ┌──────────┐
│ 前端 │ ─────────────────────────→ │ NestJS   │
│      │                            │ JwtGuard │
│      │                            │ 验证签名  │
│      │                            │ 检查黑名单│
│      │ ←───────────────────────── │          │
│      │       Response             └──────────┘
└──────┘

┌──────┐  401 token expired         ┌──────────┐
│ 前端 │ ──→ POST /auth/refresh ──→ │ NestJS   │
│      │ ←── { new access_token } ─ │          │
└──────┘                            └──────────┘
```

### 7.2 RBAC 权限模型

```
Role → Permission → Resource:Action
admin → *:*                     (全部权限)
doctor → patients:read/write    (患者读写)
       → diagnosis:*            (诊断全部)
       → medications:prescribe  (开处方)
nurse  → patients:read          (患者只读)
       → records:write          (病历写入)
researcher → research:*         (科研全部)
            → patients:read/anonymized (匿名化患者数据)
auditor → audit-log:read        (审计日志只读)
         → (无写权限)
```

### 7.3 PHI 保护

| 层 | 措施 |
|----|------|
| 传输 | TLS 1.3 强制（HSTS + preloading） |
| 存储 | 数据库字段级 AES-256-GCM 加密 |
| 备份 | 加密备份 + 异地存放 |
| 访问 | RBAC + 字段级权限（医生只能看自己患者） |
| 审计 | 所有 PHI 读写记录到不可篡改的 AuditLog |
| 脱敏 | 日志中自动脱敏（手机号 → `138****5678`） |

### 7.4 密码安全

- 哈希算法：**argon2id**（memory=64MB, iterations=3, parallelism=4）
- 密码策略：≥10 位,包含大小写+数字+特殊符号
- 登录失败锁定：5 次失败后锁定 15 分钟
- 密码重置：一次性 token，30 分钟过期

## 10. 合规与审计

### 10.1 审计日志设计

```prisma
model AuditLog {
  id          BigInt   @id @default(autoincrement())
  userId      String
  action      String   // CREATE | READ | UPDATE | DELETE | LOGIN | LOGOUT
  resource    String   // Patient | MedicalRecord | Diagnosis | ...
  resourceId  String?
  ip          String
  userAgent   String
  metadata    Json     // 变更前后的 diff
  timestamp   DateTime @default(now())
  hash        String   // 前一条记录的 hash,形成链式结构(防篡改)

  @@index([userId, timestamp])
  @@index([resource, resourceId])
}
```

### 10.2 数据保留策略

| 数据类型 | 保留期 | 依据 |
|----------|--------|------|

## 13. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Prisma 从 MySQL 切 PostgreSQL 有兼容问题 | 低 | 中 | 先跑 `prisma validate` + `prisma migrate diff`，充分测试 |

| LLM 推理延迟超标(>5s) | 中 | 高 | 流式响应(SSE) + 缓存常见问答 + 降级到关键词匹配 |
| pgvector 检索质量不足 | 低 | 中 | 预留切换到 Milvus/Qdrant 的接口抽象 |
| 等保三级测评不通过 | 中 | 高 | Week 9 预留自查；选择有医疗等保经验的测评机构 |
| 医院内网部署无法用云 GPU | 高 | 中 | 本地部署 Ollama + 开源模型(Qwen-14B/DeepSeek-R1-Distill) |
| 双语言(TS+Python)增加沟通成本 | 中 | 中 | 用 OpenAPI/proto 契约驱动,接口文档先行 |
